[![Data: CC0 1.0](https://img.shields.io/badge/data-CC0%201.0-lightgrey.svg)](CREDITS.md)
[![Dataset DOI](https://img.shields.io/badge/dataset%20DOI-10.25678%2F000D3C-orange.svg)](https://doi.org/10.25678/000D3C)

Code accompanying the manuscript **"Edge-Enabled UV-Vis Spectroscopy for Real-Time Wastewater Monitoring:
Secondary-Data Validation and a Roadmap toward UV-Vis-Raman Fusion"** (Prince Kumar, Harshpreet Kaur), currently
under review. The repository contains the code, configurations and machine-readable outputs needed to reproduce
every analysis. The interpretation of the results, the figures and the discussion are in the manuscript; figures
are not stored here and are regenerated by the scripts listed below. The raw dataset is obtained from its
original open source and is not redistributed.

## Abstract

Sewage treatment plants (STPs) rely largely on laboratory analysis, although online UV-Vis analysers are already part of India's continuous-monitoring framework for STP effluent. We propose an edge-enabled UV-Vis-Raman monitoring framework and test its UV-Vis prediction core on an open 25-week dataset of raw municipal wastewater (510 spectra matched to grab samples). Partial least-squares (PLS) regression predicted ammonium with R² = 0.86 under random and 0.82 under time-blocked cross-validation, and phosphate with 0.66 and 0.56; dissolved organic carbon was not recoverable. PLS outperformed a compact one-dimensional convolutional neural network (CNN), also when tuned, for ammonium and phosphate, with about 1,450 times fewer operations. On a Raspberry Pi 4, the complete PLS pipeline took 4.2 ms per spectrum (model step 0.19 ms; CNN 2.8 ms), and a 24 h test over a VPN with injected and unplanned outages lost no messages. A physics-informed simulation, not a validation, indicated that Raman would add little for nitrate but could greatly reduce nitrite error; sensitivity analysis and a test on the real spectra place the required Raman signal-to-noise ratio at about 100. The results are a reproducible baseline, not evidence of an integrated device; staged acceptance criteria are defined for the hardware and pilot stages.

## Repository layout

| Path | Content |
|---|---|
| `run_experiment.py` | Data matching, preprocessing, PLS and 1D-CNN, random and time-blocked cross-validation; writes `results/batch-N_<tag>/` |
| `block_spans.py` | Date range of each time-blocked fold |
| `validation/` | Repeated CV with corrected t-test and block bootstrap; tuned CNN and learning curves; baselines, forward-chaining and purged CV, VIP; fouling test on the logged cleanings |
| `bench_edge.py`, `fleet/` | Inference benchmark; Docker/QEMU Raspberry-Pi-class profiles; MQTT fleet, fault injection and soak-test scripts; outage analysis |
| `simulation/` | In-silico UV-Vis + Raman design study, Morris sensitivity analysis, real-matrix semi-synthetic test |
| `figures/` | Scripts for the diagrams and the graphical abstract |
| `results/`, `fleet/out_bench*`, `fleet/real_pi`, `fleet/runs`, `simulation/*.json/csv` | Machine-readable outputs (CSV, JSON, logs) of the runs |

## Reproduce

All runs use fixed seeds. `run_experiment.py` creates a local `.venv` and installs its dependencies; without the real
data file it runs on clearly labelled synthetic data stamped "NOT FOR PUBLICATION".

**Secondary-data validation** (215 spectral channels; `--spectral-only` is off by default so that v1.0.1 stays reproducible):

```bash
python run_experiment.py --spectral-only --targets "nh4,po4,doc" --kfold 5 --tag raw_215ch
python run_experiment.py --spectral-only --targets "nh4,po4,doc" --kfold 5 --smooth --snv --tag smoothsnv_215ch
python run_experiment.py --spectral-only --targets "nh4,po4,doc" --kfold 5 --cv blocked --tag raw_blocked_215ch
python run_experiment.py --spectral-only --targets "nh4,po4,doc" --kfold 5 --smooth --snv --cv blocked --tag smoothsnv_blocked_215ch
python block_spans.py
```

**Statistical and fairness checks:**

```bash
python validation/stats_repeated_cv.py data/raw/extracted results/validation_v130
python validation/cnn_tuning_learning_curve.py data/raw/extracted results/validation_v130
python validation/baselines_forward.py data/raw/extracted results/validation_v131
python validation/drift_cleaning_real.py data/raw/extracted/2_data results/validation_v130
```

**Edge benchmark, emulated fleet and soak test** (Docker with buildx; QEMU/binfmt for arm64 and arm/v7):

```bash
python fleet/export_model.py --data-root data/raw/extracted      # deployable PLS coefficients + replay spectra
python3 bench_edge.py --repeats 2000 --sustain 30 --label pi4-real --out bench_pi_real.json   # on a physical Pi
cd fleet
./run_bench_matrix.sh                                # emulated profiles (run_bench_matrix_win.sh on Windows)
COMPOSE_BUILD=--build ./run_fleet.sh 1 1800 my_run   # MQTT fleet replaying real spectra at 1 Hz for 30 min;
                                                      # writes runs/my_run/ including analyse.txt and fleet_summary.csv
BROKER_IP=<host VPN IP> PI_SSH="<remote shell command>" ./run_soak.sh 1 86400 14400 soak_24h   # rate, duration s, restart every s
python soak_outages.py runs/soak_24h                 # outages, delivery and latency outside outages
python plot_fleet.py runs/my_run figs
```

Emulated profiles enforce real memory and CPU limits, but their CPU speed is that of the emulator, not of a
Raspberry Pi; label emulated timings accordingly.

**In-silico design study** (simulation, not a validation):

```bash
python simulation/export_real.py data/raw/extracted simulation/real510.npy   # repo root; real spectra, not committed
cd simulation
python sim_fusion.py && python analyse.py && python plot_drift.py
python robust_sensitivity.py && python robust_realmatrix.py real510.npy && python robust_plot.py
```

**Diagrams:** `python figures/make_figures.py figures/out` and `python figures/make_graphical_abstract.py figures/out`.

(Python 3.11.2, NumPy 1.24.2, SciPy 1.10.1, scikit-learn 1.2.1, paho-mqtt 1.6.1), Eclipse Mosquitto 2.
